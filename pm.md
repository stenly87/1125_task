## Часть 1. Работа с локальным репозиторием

**Задача:** Создать проект с нуля, внести изменения и зафиксировать их в истории.

1. **Создайте папку для проекта и перейдите в нее:**
   <details>
      <summary>Bash</summary>
   
         mkdir my_project
         cd my_project   
   </details>
2. **Инициализируйте локальный репозиторий:**   
   <details>
      <summary>Bash</summary>
      
         git init
   </details>  

4. **Создайте первый файл и добавьте его в индекс:**
   <details>
      <summary>Bash</summary>
   
         echo "Привет, Git!" > readme.txt
         git status  # Посмотрите статус: файл не отслеживается (untracked)
         git add readme.txt
         git status  # Теперь файл в индексе (staged)
   </details>
5. **Сделайте первый коммит (фиксацию):**
   <details>
      <summary>Bash</summary>
         
         git commit -m "Начальный коммит: добавлен readme"
    </details>
6. **Внесите изменения в файл, просмотрите их и зафиксируйте:**
   Откройте `readme.txt` и допишите вторую строку: `Это мой первый проект.`
   <details>
      <summary>Bash</summary>
      
         git status  # Файл изменен (modified)
         git diff    # Посмотрите, что именно изменилось
         git add readme.txt
         git commit -m "Добавлено описание проекта"
   </details>
7. **Просмотрите историю коммитов:**
   <details>
      <summary>Bash</summary>
      
         git log
         # Для более наглядного графического вывода:
         git log --oneline --graph
   </details>

## Часть 2. Работа с удаленным репозиторием

**Задача:** Опубликовать локальный репозиторий на внутреннем сервере и получить изменения с сервера.

### Шаг 2.1. Создание репозитория на сервере

1. Откройте браузер и перейдите по адресу: `http://192.168.200.35:3000`
2. Войдите в систему, используя выданные преподавателем логин и пароль.
3. Нажмите кнопку **«Создать репозиторий»** (`Символ + сверху справа`).
4. Заполните поля:
   * **Имя репозитория:** `lab-git-<ваш_логин>` (например, `lab-git-user1`).
   * **Описание:** Лабораторная работа по Git.

   * **Инициализация:** **СНИМИТЕ** все галочки (не создавайте Readme, .gitignore и лицензию, так как у нас уже есть локальный репозиторий).

### Шаг 2.2. Очистка старых учётных данных Windows
Если у вас линукс, пропускайте этот шаг. Просто проверьте, существует ли файл .git-credentials в домашней папке.

3. Откройте вкладку **«Учётные данные Windows»**.
4. В списке найдите все записи, связанные с адресом `192.168.200.35` (например, `git:192.168.200.35` или `192.168.200.35`).
5. Для каждой такой записи раскройте её и нажмите кнопку **«Удалить»**.
6. Убедитесь, что в списке больше нет записей, относящихся к `192.168.200.35`.

*После очистки при следующем подключении к серверу Git запросит логин и пароль заново, и вы введёте актуальные данные, выданные преподавателем.*

### Шаг 2.3. Связывание локального и удаленного репозитория

Вернитесь в терминал в папку `my_project`.

1. **Добавьте удаленный сервер (origin):**

## Часть 3. Имитация командной работы и разрешение конфликтов

**Задача:** Научиться получать изменения (`pull`) и разрешать конфликты слияния.  
*Для имитации работы "второго разработчика" создадим еще одну папку на вашем компьютере.*

1. **Склонируйте репозиторий в новую папку (имитация компьютера коллеги):**
   <details>
      <summary>Bash</summary>
      
         cd ..
         git clone http://192.168.200.35:3000/<ваш_логин>/lab-git-<ваш_логин>.git colleague_workspace
         cd colleague_workspace
   </details>

2. **Внесите изменения от имени "коллеги" и залейте в удаленный репозиторий:**
   Откройте `readme.txt` в папке `colleague_workspace` и измените первую строку на: `Привет, Git! Это изменил коллега.`
   <details>
      <summary>Bash</summary>
      
         git add readme.txt
         git commit -m "Изменение от коллеги"
         git push
   </details>

3. **Вернитесь в свою основную рабочую папку:**
   <details>
      <summary>Bash</summary>
         
         cd ../my_project
   </details>

5. **Внесите изменения в ТОТ ЖЕ самый файл от "своего" имени:**
   Откройте `readme.txt` в `my_project` и измените первую строку на: `Привет, Git! Это изменил я.`
   <details>
      <summary>Bash</summary>
      
         git add readme.txt
         git commit -m "Мое изменение"
   </details>

6. **Попробуйте отправить изменения на сервер:**
   <details>
      <summary>Bash</summary>
         
         git push
   </details>
   *Сервер отклонит push, так как на сервере есть изменения, которых нет у вас локально.*

7. **Получите изменения с сервера (возникнет конфликт):**
   <details>
      <summary>Bash</summary>
   
         git pull
   </details>
   Git выдаст ошибку: `CONFLICT (content): Merge conflict in readme.txt`.

8. **Разрешите конфликт:**
   Откройте файл `readme.txt` в любом текстовом редакторе. Вы увидите служебные метки Git:
   ```text
   <<<<<<< HEAD
   Привет, Git! Это изменил я.
   =======
   Привет, Git! Это изменил коллега.
   >>>>>>> [хэш коммита коллеги]
   ```
   **Ваша задача:** удалить эти служебные метки (`<<<`, `===`, `>>>`) и оставить в файле тот текст, который вы считаете правильным (или объединить их). Сохраните файл.

9. **Завершите слияние:**
   <details>
      <summary>Bash</summary>
      
         git add readme.txt
         git commit -m "Разрешен конфликт слияния"
         git push
   </details>

## Часть 4. Работа с ветками и Pull Request

**Задача:** Освоить создание feature-веток и механизм ревью кода через веб-интерфейс.

1. **Создайте новую ветку (`feature/new-text`) и переключитесь на нее:**
   <details>
      <summary>Bash</summary>
      
         git checkout -b feature/new-text
         # (или git switch -c feature/new-text в новых версиях Git)
   </details>

2. **Создайте новый файл и сделайте коммит:**
   <details>
      <summary>Bash</summary>
      
         echo "Новый функционал" > feature.txt
         git add feature.txt
         git commit -m "Добавлен новый функционал"
   </details>

3. **Отправьте ветку на удаленный сервер:**
   <details>
      <summary>Bash</summary>
      
         git push origin feature/new-text
   </details>

4. **Создание Pull Request в веб-интерфейсе:**
   * Зайдите на страницу вашего репозитория на сервере `192.168.200.35:3000`.
   * Откройте страницу с ветками. Там появится вторая ветка `feature/new-text`. Справа от названия нажмите кнопку **«Новый запрос на слияние»**
   * Заполните заголовок и описание. Нажмите **«Создать запрос на слияние»**.
   * Нажмите **«Слить пулл-реквест»**.
   * Слитую ветку можно удалить.

5. **Синхронизируйте локальную основную ветку:**
   Вернитесь в терминал, переключитесь на главную ветку и скачайте обновления:
   <details>
      <summary>Bash</summary>
      
         git checkout master
         git pull
   </details>

## Часть 5. Форк чужого репозитория и Pull Request

**Задача:** Освоить механизм форка (fork) и внесения вклада (contribute) в чужой проект через Pull Request.  
*Для выполнения этого задания объединитесь в пары с одногруппником. Далее в инструкции: **Студент А** и **Студент Б**.*

### Шаг 5.1. Создание форка (делает Студент А)

1. **Студент А** открывает в браузере репозиторий **Студента Б** по адресу:  
   `http://192.168.200.35:3000/<логин_Б>/lab-git-<логин_Б>`
2. В правом верхнем углу нажимает кнопку **«Ответвить»** (Fork).
3. Сервер создаст копию репозитория в аккаунте Студента А:  
   `http://192.168.200.35:3000/<логин_А>/lab-git-<логин_Б>`

### Шаг 5.2. Клонирование форка и внесение изменений (делает Студент А)

1. **Студент А** клонирует **свой форк** на локальный компьютер:
   <details>
      <summary>Bash</summary>
      
         cd ..
         git clone http://192.168.200.35:3000/<логин_А>/lab-git-<логин_Б>.git
         cd lab-git-<логин_Б>
   </details>

2. Создаёт новую ветку (`feature/contribution_(ИмяЮзера)`) для своего вклада:
   <details>
      <summary>Bash</summary>
      
         git checkout -b feature/contribution_(ИмяЮзера)
     </details>

3. Вносит изменения. Например, создаёт новый файл `contributor.txt`:
   <details>
      <summary>Bash</summary>
      
         echo "Вклад в проект от Студента А" > contributor.txt
         git add contributor.txt
         git commit -m "Добавлен файл contributor.txt"
     </details>

4. Отправляет ветку в **свой форк** на сервер:
   <details>
      <summary>Bash</summary>
         
         git push origin feature/contribution_(ИмяЮзера)
     </details>

### Шаг 5.3. Создание Pull Request из форка (делает Студент А)

1. **Студент А** открывает в браузере страницу **своего форка** на сервере.
2. Нажимает кнопку **«Создать Pull Request»** для только что запушенной ветки (Ярко-зеленая кнопка рядом с названием ветки).
3. **Важный момент:** проверяет, что Pull Request направлен **в оригинальный репозиторий Студента Б** (а не в свой собственный). В интерфейсе это обычно отображается как:  
   `<логин_А>:feature/contribution` → `<логин_Б>:master`
4. Заполняет заголовок и описание изменений, нажимает **«Создать Pull Request»**.

### Шаг 5.4. Ревью и принятие Pull Request (делает Студент Б)

1. **Студент Б** получает уведомление (или заходит на страницу своего репозитория) и видит входящий Pull Request (Вкладка **«Запросы на слияние»**).
2. Открывает Pull Request, просматривает предложенные изменения (вкладка **Files** / **Файлы**).
3. Может оставить комментарии к коду (опционально).
4. Нажимает кнопку **«Слить пулл-реквест»** (Merge Pull Request), затем подтверждает слияние.

### Шаг 5.5. Синхронизация локальных репозиториев (делают оба студента)

1. **Студент Б** подтягивает изменения в свой локальный репозиторий:
   <details>
      <summary>Bash</summary>
      
         git pull origin master
     </details>
   Теперь в его репозитории появился файл `contributor.txt`.

2. **Студент А** синхронизирует свой форк с оригинальным репозиторием, чтобы в будущем избежать расхождений:
   * В веб-интерфейсе Gogs нет автоматической синхронизации, в отличие от гитхаба, поэтому нужно обновить локальный репозиторий из оригинального и потом обновить свой репозиторий:
   1. Добавляем оригинальный удаленный репозиторий в наш локальный (называем, например, `upstream`)
   2. Выполняем фетч (обновление) из добавленного репозитория
   3. Переключаемся на основную локальный ветку (`master`)
   4. Сливаем наш мастер с удаленным мастером `upstream/master`
   5. Заливаем изменения в наш основной удаленный репозиторий
   <details>
      <summary>Bash</summary>
      
         git remote add upstream http://192.168.200.35:3000/<логин_Б>/lab-git-<логин_Б>.git
         git fetch upstream
         git checkout master
         git merge upstream/master
         git push origin master
     </details>

## Часть 6. Путешествие во времени: откаты и возвраты

**Задача:** Научиться безопасно отменять изменения, возвращаться к предыдущим состояниям проекта и создавать новые ветки из прошлого.

### Шаг 6.1. Подготовка «ошибочного» коммита
Чтобы было что откатывать, давайте специально сделаем ошибку.

1. Откройте файл `readme.txt` в вашей основной папке (`my_project`).
2. Допишите в конец файла строку: `ОШИБКА: Этот текст лишний и портит документ.`
3. Зафиксируйте это изменение:
   ```bash
   git add readme.txt
   git commit -m "Добавлен важный апдейт"  # На самом деле это ошибка!
   ```

### Шаг 6.2. Отмена последнего коммита (Soft Reset)
Представим, что вы заметили ошибку сразу после коммита, но хотите сохранить изменения в файле, чтобы исправить их вручную.

1. Выполните команду «мягкого» сброса:
   ```bash
   git reset --soft HEAD~1
   ```
   *`HEAD~1` означает «предыдущий коммит относительно текущего».*

2. Проверьте статус:
   ```bash
   git status
   ```
   **Результат:** Коммит исчез из истории, но файл `readme.txt` остался измененным (в индексе). Вы можете отредактировать файл, убрать лишнюю строку и сделать коммит заново с правильным сообщением.

3. **Исправьте коммит:**
   ```bash
   git commit -m "Исправлено сообщение коммита"
   ```

### Шаг 6.3. Жесткий откат изменений (Hard Reset)
Теперь представим более серьезную ситуацию: вы сделали несколько коммитов, но поняли, что всё пошло не так, и нужно вернуться к состоянию «как было вчера», полностью удалив все промежуточные изменения.

1. Посмотрите историю, чтобы найти хеш «хорошего» коммита (например, того, что был до наших экспериментов):
   ```bash
   git log --oneline
   ```
   Скопируйте хеш (первые 7 символов) нужного коммита. Пусть это будет `a1b2c3d`.

2. Выполните «жесткий» сброс:
   ```bash
   git reset --hard a1b2c3d
   ```
   **Внимание!** Эта команда безвозвратно удаляет все изменения в файлах и коммитах, сделанные после указанного хеша. Файл `readme.txt` вернется в то состояние, в котором он был в момент коммита `a1b2c3d`.

3. Проверьте содержимое файла и историю:
   ```bash
   cat readme.txt
   git log --oneline
   ```

### Шаг 6.4. Просмотр прошлого и ответвление (Checkout & Branching)
Иногда нужно не просто откатить текущую ветку, а посмотреть, как проект выглядел в прошлом, или начать новую фичу от старого состояния.

1. **Посмотрите состояние репозитория в прошлом:**
   Найдите хеш самого первого коммита («Начальный коммит»).
   ```bash
   git checkout <хеш_первого_коммита>
   ```
   *Git предупредит, что вы находитесь в состоянии «detached HEAD». Это нормально.*
   Посмотрите файлы в папке — там будет только первоначальный `readme.txt` с одной строкой.

2. **Создайте ветку из этого прошлого:**
   Не выходя из этого состояния, создайте новую ветку, которая начнет расти от этого старого коммита:
   ```bash
   git checkout -b experiment-from-past
   ```

3. Внесите изменения в этой новой ветке:
   ```bash
   echo "Экспериментальная версия из прошлого" > experiment.txt
   git add experiment.txt
   git commit -m "Начало эксперимента"
   ```

4. Вернитесь в основную ветку:
   ```bash
   git checkout main
   ```
   Обратите внимание: файл `experiment.txt` исчез из папки, так как он существует только в ветке `experiment-from-past`. Основная ветка `main` осталась чистой.

### Шаг 6.5. Отмена опубликованных изменений (Revert)
Если вы уже отправили ошибочный коммит на сервер (`git push`), использовать `reset --hard` опасно, так как это переписывает историю и ломает работу коллегам. В таких случаях используют `revert`.

1. Представим, что мы запушили какой-то коммит, который нужно отменить, не стирая его из истории.
2. Создайте новый коммит, который делает ровно противоположное действие:
   ```bash
   git revert HEAD
   ```
   *(Откроется редактор для сообщения коммита. Просто сохраните и закройте его).*

3. Теперь в истории появился новый коммит «Revert ...», который отменяет изменения предыдущего. Это безопасный способ отката для публичных репозиториев.

### Задание А. Настройка `.gitignore`
Часто в проектах появляются временные файлы, логи или скомпилированные бинарники, которые **не нужно** хранить в репозитории.

1. В своем локальном репозитории (`my_project`) создайте файл `.gitignore`.
2. Добавьте в него следующие строки (имитация типичного проекта):
   ```text
   # Временные файлы
   *.tmp
   *.log
   
   # Папки с зависимостями или сборкой
   node_modules/
   build/
   
   # Файлы настроек IDE
   .vscode/
   .idea/
   ```
3. Создайте «мусорные» файлы, чтобы проверить работу ignore:
   ```bash
   touch error.log
   mkdir node_modules
   touch node_modules/package.json
   touch secret.tmp
   ```
4. Выполните `git status`. Убедитесь, что созданные файлы **не отображаются** как неотслеживаемые.
5. Зафиксируйте сам файл `.gitignore`:
   ```bash
   git add .gitignore
   git commit -m "Добавлен .gitignore для фильтрации мусора"
   git push origin main
   ```

### Задание Б. Работа с тегами (Версионирование)
Git позволяет помечать важные коммиты тегами (например, релизами v1.0, v2.0).

1. Посмотрите историю коммитов: `git log --oneline`.
2. Выберите хеш самого первого коммита («Начальный коммит»).
3. Создайте легковесный тег для этого коммита:
   ```bash
   git tag v1.0 <хеш_первого_коммита>
   ```
4. Создайте аннотированный тег для текущего состояния (последнего коммита):
   ```bash
   git tag -a v2.0 -m "Релиз версии 2.0 с поддержкой форков"
   ```
5. Отправьте теги на сервер:
   ```bash
   git push origin --tags
   ```
6. Проверьте в веб-интерфейсе Gogs: перейдите во вкладку **«Релизы»** (Releases) или **«Теги»** (Tags) — ваши метки должны появиться там.
